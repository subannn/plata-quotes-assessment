# FX Quotes Service — устройство сервиса

Краткое описание того, как реализуется сервис из [PlataAssignment.MD](PlataAssignment.MD).

## Общая схема

```
Клиент ──POST /quotes/updates──► HTTP API ──INSERT (pending)──► quote_updates
       ◄──── 202 {update_id} ─────┘

Воркер (раз в worker.poll_interval) ──забирает пачку pending──► группирует по base ──► exchangerates.Client.GetRates
       ──INSERT rates, UPDATE quote_updates (done / failed)──► PostgreSQL

Клиент ──GET /quotes/updates/{id}──► HTTP API ──SELECT──► статус, цена, время
Клиент ──GET /quotes/latest───────► HTTP API ──SELECT──► последняя цена по паре
```

Хендлеры к провайдеру не ходят: они только пишут и читают БД. Запрос к провайдеру выполняет фоновый воркер.

## Компоненты

| Компонент | Где | Назначение |
|---|---|---|
| HTTP API | `api/` (ogen, из `openapi.yaml`), `implementations/handler.go` | Валидация запроса, работа с БД, маппинг ошибок в HTTP-коды |
| Repository | `internal/database/` | SQL-запросы к PostgreSQL (pgx) |
| exchangerates.Client | `internal/exchangerates/client.go` | Клиент exchangeratesapi.io: `GetRates(ctx, base, quotes...)` — курсы base к нескольким валютам одним запросом |
| Worker | `implementations/worker.go` | Фоновая обработка заявок |
| Config | `internal/config/config.go` | Загрузка и проверка JSON-конфига |
| main | `cmd/service/main.go` | Конфиг, запуск HTTP-сервера и воркера, graceful shutdown |

## Модель данных

Схема — `migration/init.up.sql`. Сервис её не применяет: в Docker Compose её применяет PostgreSQL при создании новой базы в новом контейнере (`docker-entrypoint-initdb.d`; база хранится внутри контейнера, без тома), при локальном запуске — вручную.

- **`rates`** — полученные от провайдера курсы; заодно кеш курсов (см. «Кеш курсов»). Уникальность `(base, quote, rate_updated_at)`: один и тот же курс провайдера хранится один раз. `rate_updated_at` — время курса у провайдера, `fetched_at` — когда провайдер последний раз вернул этот курс.
- **`quote_updates`** — заявки на обновление. Одна заявка — одна пара.

Жизненный цикл заявки:

```
pending ──воркер забрал──► processing ──курс получен──► done   (rate_id → rates)
   ▲                           │
   └──── есть попытки ─────────┤  ошибка или lock_timeout
                               └── попытки кончились ──► failed (error)
```

Из `processing` заявка уходит по ошибке обработки или по `worker.lock_timeout` (зависла, см. «Зависшие заявки»). Дальше в обоих случаях одинаково: есть попытки — обратно в `pending`, кончились — `failed`.

## API

| Метод | Что делает |
|---|---|
| `POST /quotes/updates` | Создаёт заявку `pending`, отвечает `202 {update_id}`. Обновление не выполняет. |
| `GET /quotes/updates/{id}` | Статус заявки. При `done` — цена и время курса у провайдера, при `failed` — причина. |
| `GET /quotes/latest?base=&quote=[&at=]` | Последний курс пары из `rates` (по `rate_updated_at`). С `at` — последний курс на этот момент или раньше. |

Цена отдаётся строкой, чтобы не терять точность.

**Идемпотентность.** `POST /quotes/updates` требует заголовок `Idempotency-Key` (UUID); без него — `400`. Повтор с тем же ключом и той же парой возвращает уже созданную заявку (`202` с тем же `update_id`), новая не создаётся. Тот же ключ с другой парой — `409 Conflict`.

**Ошибки.**

| Ситуация | Код |
|---|---|
| Невалидный запрос, `base == quote` | 400 |
| Нет/неверный `X-API-Key` | 401 |
| Заявка или курс не найдены | 404 |
| Конфликт `Idempotency-Key` | 409 |
| Прочее | 500 |

## Воркер

Очередь заявок — сама таблица `quote_updates`, отдельный брокер не нужен.

**Когда просыпается.** Периодически, по тикеру раз в `worker.poll_interval`: каждый тик воркер проверяет БД на заявки `pending`. Хендлеры с воркером напрямую не связаны — всё общение через таблицу. Поэтому заявки не теряются при рестарте, повторные попытки подбираются следующим тиком, а несколько экземпляров сервиса работают с одной очередью. Задержка обработки новой заявки — до одного интервала.

**Один цикл:**

1. **Забрать пачку.** Атомарно переводит до `worker.batch_size` заявок из `pending` в `processing`:

   ```sql
   UPDATE quote_updates
   SET status = 'processing', locked_at = now(), attempts = attempts + 1, updated_at = now()
   WHERE id IN (
       SELECT id FROM quote_updates
       WHERE status = 'pending'
       ORDER BY created_at
       LIMIT $1
       FOR UPDATE SKIP LOCKED
   )
   RETURNING id, base, quote;
   ```

   `SKIP LOCKED` позволяет запускать несколько экземпляров сервиса без двойной обработки.

2. **Сгруппировать по base.** Заявки `USD/MXN`, `USD/EUR`, `USD/MXN` → одна группа `USD` с quote `MXN`, `EUR`.

3. **Закрыть из кеша.** Пары группы, по которым есть свежий курс, закрываются им сразу, без провайдера (см. «Кеш курсов»).

4. **Сходить к провайдеру** за оставшимися парами — один вызов на группу: `GetRates(ctx, "USD", "MXN", "EUR")`. Если все пары закрыты из кеша, вызова нет.

5. **Сохранить результат** в одной транзакции на группу:
   - `INSERT INTO rates ... ON CONFLICT (base, quote, rate_updated_at) DO UPDATE SET ..., fetched_at = now() RETURNING id` — если такой курс уже есть, берётся его `id`, а `fetched_at` обновляется: провайдер только что подтвердил курс;
   - заявки → `done`, проставляется `rate_id`.

6. **Ошибка.** Ошибка провайдера, ошибка сохранения результата (шаг 5) или закрытия заявок из кеша (шаг 3): если `attempts < worker.max_attempts` — заявки возвращаются в `pending` и будут взяты следующим циклом; иначе — `failed` с причиной в `error`: для ошибки провайдера — её текст, для ошибок БД (шаги 3 и 5) — `internal error` (подробности — только в логе, клиенту не отдаются).

**Кеш курсов.** Чтобы не спрашивать провайдера о том, что он только что сообщил, курс пары считается свежим `worker.rate_ttl` с момента, когда провайдер его вернул (`fetched_at`). Пока курс свежий, заявки по паре закрываются им без запроса к провайдеру. Итог: к провайдеру уходит не больше одного запроса на base за `rate_ttl`, сколько бы заявок ни пришло; без заявок запросов нет вовсе.

- Кеш — та же таблица `rates`: общий для всех экземпляров, переживает рестарт; свежесть считается по `now()` БД.
- `fetched_at` обновляет только ответ провайдера. Закрытие заявки из кеша курс не трогает — иначе при постоянном потоке заявок кеш никогда бы не устаревал.
- Если свежих курсов по паре несколько, берётся самый новый по `rate_updated_at`.
- Ошибка чтения кеша заявки не валит: воркер идёт к провайдеру по всем парам.
- `rate_ttl` разумно брать равным периоду обновления курсов у провайдера; `0` выключает кеш.

**Зависшие заявки.** Если процесс упал посреди обработки, заявка останется в `processing`. Отдельный проход раз в цикл возвращает в `pending` заявки с `locked_at` старше `worker.lock_timeout`; если попытки кончились (`attempts >= worker.max_attempts`) — переводит в `failed` с ошибкой `processing timed out`. Для этого есть индекс `quote_updates_processing_idx`.

**Параллельность.** В процессе работает один воркер (одна горутина). Благодаря группировке по base за цикл получается не больше одного запроса к провайдеру на каждую base, так что нескольких горутин в одном процессе не нужно. Масштабирование — числом экземпляров сервиса: `SKIP LOCKED` делит между ними одну очередь. Пропускная способность одного воркера — `worker.batch_size` заявок за `worker.poll_interval`. Вызовы провайдера ограничены таймаутом HTTP-клиента (10 с); отмена контекста при остановке их не прерывает — начатая пачка доделывается.

## Конфигурация

Вся конфигурация — в JSON-файле (пример — `config.json` в корне). Путь задаётся флагом `-config`, по умолчанию `config.json`. Загрузка и проверка — `internal/config`; неизвестные поля и пустые обязательные значения — ошибка при старте.

```json
{
  "http": {
    "addr": ":8080",
    "api_key": "change-me"
  },
  "database": {
    "url": "postgres://postgres:postgres@localhost:5435/quotes?sslmode=disable"
  },
  "exchange_rates": {
    "url": "https://api.exchangeratesapi.io/v1",
    "access_key": "change-me"
  },
  "worker": {
    "batch_size": 100,
    "poll_interval": "1s",
    "max_attempts": 3,
    "lock_timeout": "1m",
    "rate_ttl": "1m"
  }
}
```

| Поле | Назначение |
|---|---|
| `http.addr` | Адрес HTTP-сервера, напр. `:8080` |
| `http.api_key` | Ключ для `X-API-Key` |
| `database.url` | DSN PostgreSQL |
| `exchange_rates.url` | Базовый URL провайдера (по умолчанию `https://api.exchangeratesapi.io/v1`) |
| `exchange_rates.access_key` | Ключ exchangeratesapi.io |
| `worker.batch_size` | Размер пачки заявок |
| `worker.poll_interval` | Как часто воркер проверяет новые заявки, напр. `1s` |
| `worker.max_attempts` | Максимум попыток на заявку |
| `worker.lock_timeout` | Через сколько `processing` считается зависшей, напр. `1m` |
| `worker.rate_ttl` | Сколько курс от провайдера считается свежим, напр. `1m`; `0s` — без кеша |

**Как подбирать параметры воркера.**

- `poll_interval` и `batch_size` — скорость обработки: новая заявка ждёт до одного `poll_interval`, один экземпляр обрабатывает до `batch_size` заявок за интервал. На число запросов к провайдеру не влияют.
- `rate_ttl` — нагрузка на провайдера: не больше одного запроса на base за `rate_ttl`. Разумно брать равным периоду обновления курсов у провайдера: меньше — лишние запросы за тем же курсом, больше — клиенты получают устаревший курс.
- `max_attempts` — сколько ошибок подряд терпит заявка. Повторы идут каждый тик без нарастающей паузы, так что заявка сдаётся примерно через `max_attempts × poll_interval`.
- `lock_timeout` должен быть заметно больше самой долгой обработки пачки (таймаут запроса к провайдеру — 10 с на каждую base в пачке). Иначе заявку вернут в очередь, пока живой воркер её ещё обрабатывает, и она будет обработана дважды. Слишком большой — заявки после падения процесса дольше ждут.

## Запуск и остановка

- При старте: подключение к БД, поднимаются HTTP-сервер и воркер. Схему БД сервис не применяет (см. «Модель данных»).
- По `SIGINT`/`SIGTERM`: сервер перестаёт принимать запросы и дожидается текущих, воркер доделывает текущую пачку и выходит. Недоделанные заявки подберёт механизм зависших заявок.
- Локально — `docker compose up --build` (сервис + PostgreSQL); конфиг — `config.docker.json`, монтируется в контейнер.
